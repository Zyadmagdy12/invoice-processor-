# العينة 3 — Invoice Processor: خطة مختصرة + To-Do

**التاريخ:** 2026-11-22. **الحالة:** التصميم معتمد ومجمّد (نقاش جولتين مع ChatGPT + توضيح أولوية البورتفليو + 5 تفاصيل تنفيذية نهائية).
**الهدف:** عينة Portfolio شغالة فعلاً: مطابقة فواتير 3-Way (فاتورة / أمر شراء / استلام) بقواعد حتمية، مع مراجعة بشرية وسجل تدقيق. مش SaaS، ولا ERP، ولا بنية تحتية لإنتاج افتراضي.

## القرارات المعتمدة (لا إعادة نقاش)

1. **البورتفليو أولاً:** عينة مقنعة قابلة للعرض، مش نظام إنتاج. المعالجة المتسلسلة هي الحد المعلن للديمو؛ التزامن خارج النطاق وموثق كقيد، بلا هندسة حوله.
2. **محرك مطابقة حتمي من 7 مراحل** (تفاصيله في `schema.md`)، وOCR طبقة إدخال فقط. كل المبالغ جنيه صحيح (integer piastres)؛ أي فرق ≥ قرش واحد فرق حقيقي.
3. **تساهل صفري تلقائياً:** المطابقة التلقائية = تطابق تام بعد تقريب حتمي. فوق الصفر: فرق سعر ≤ 50 جنيه للسطر (ثابت واحد `PRICE_REVIEW_MAX_EGP = 50`) **و** مجموع القيم المطلقة لفروق السطور ≤ 50 → مراجعة قابلة للموافقة كاستثناء؛ فوق ذلك → محظور غير قابل للموافقة. فرق ضريبة → محظور (تصحيح، مش استثناء).
4. **الاستهلاك التراكمي هو التميّز:** سجل Allocations append-only (إدخالات إلغاء بدل تعديل التاريخ)؛ فاتورات متعددة تسحب من نفس سطر أمر الشراء؛ `available = received − allocated`. لا استهلاك مكرر في الديمو المتسلسل.
5. **الموافقة تمر عبر المحرك:** فرع المراجعة لا يقرر ولا يكتب Allocations أبداً. بعد موافقة مصرّح بها، يُستدعى المحرك (mode=apply_exception) ليعيد التحقق من الثوابت الحرجة، ويسجّل الـ allocation، ويُنهي `exception_approved`. المرفوض أو القديم لا يستهلك شيئاً.
6. **مدخل Telegram واحد:** Workflow موحّد واحد بتريجر Telegram واحد (message + callback_query) + Router يوجّه الصور للاستقبال والضغطات للمراجعة (درس العينة 2، عيب 13). المحرك Workflow منفصل يُستدعى عبر Webhook. المجموع: **2 Workflows** فقط.
7. **المحرك يملك كل كتابات Sheets:** workflow الـ Telegram لا يكتب Sheets أبداً — إدخال/إخراج فقط (Telegram ↔ المحرك). كل انتقالات الحالة والأودت تتم داخل المحرك.
8. **التصحيح:** تعديل في Sheets + إعادة تحقق (Manual Trigger على المحرك). التصحيح ينشئ نسخة جديدة (version+1)؛ قيم النسخة السابقة تُحفظ في الـ Audit قبل قبول الجديدة. الموافقة مربوطة بـ (invoice_id, version, review_id)؛ موافقة قديمة/مكررة → محظورة.
9. **فصل الواجبات:** مُرسل الفاتورة لا يوافق عليها (فحص واحد في Apply Decision).
10. **OCR:** صور فقط، layout اصطناعي واحد؟ لا — layoutان اثنان موثقان، صفحة واحدة لكل فاتورة. لا PDF في v1. Tesseract (نفس خدمة العينة 2) + Mock OCR يرد حقولاً ثابتة حسب الـ hash.

## النطاق (صغير، ثابت)

- **داخل النطاق:** فواتير EGP فقط؛ 16 سيناريو (15 المجمّدة + S16 انحدار الجولة 4)؛ 2 Workflows (Telegram موحّد / Matching Engine)؛ 7 تابات Sheets؛ موافقة Telegram؛ Audit Log؛ ديمو 90 ثانية.
- **خارج النطاق (ممنوع):** PDF/متعدد الصفحات، عملات متعددة، خصومات (فاتورة فيها خصم تكسر الحساب → تصحيح)، تنفيذ متزامن، Schedule Trigger (يدوي فقط في v1)، ERP/محاسبة حقيقية، LLM للاستخراج.

## المعمارية (n8n 2.48.7)

```
[1] Invoice Processor — Telegram (موحّد): Telegram Trigger (message + callback_query) → Router
      → فرع الاستقبال: photo → تنزيل الصورة → OCR (HTTP) → استدعاء المحرك (Webhook mode=match)
        → إشعار بالنتيجة | Needs Review: رسالة مراجعة للمراجع فقط
      → فرع المراجعة: callback_query → تحقق من المراجع + حداثة القرار → استدعاء المحرك
        (mode=apply_exception) → تأكيد + Audit
[2] Invoice Matching Engine: Webhook (mode=match / apply_exception / revalidate)
      + Manual Trigger (إعادة تحقق جماعية: pending_receipt + correction_required)
      → 7 مراحل حتمية → كتابة الحالة + Allocations + Audit (المحرك وحده يكتب Sheets)
```

## نتيجة قابلة للقياس

- 16 سيناريو (15 + S16 انحدار): 0 فاتورة متناقضة تمر تلقائياً، ≥6 مطابقات تلقائية مشروعة، 0 استهلاك مكرر في الديمو المتسلسل، 0 موافقة غير مصرّح بها أو مكررة أو قديمة تغيّر الحالة، كل قرار له Audit event.
